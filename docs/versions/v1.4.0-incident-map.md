# v1.4.0-incident-map — operations view: incident map + Ask Sentinel on the deployed models

**Tag:** `v1.4.0-incident-map` · **Date:** 2026-09-24 · **Status:** frozen · **Current demo release**

Adds Kruthika Virupakshappa's offline incident map and on-device assistant on top of the `v1.3.0-joint` models. No model weights changed: the detector, LoRA adapter and checksums are exactly those of [v1.3.0-joint](v1.3.0-joint.md).

## What's new

| Component | Author | What it does |
|---|---|---|
| `sentinel/incident_map.py` + `static/incident_map.html` (port 8100) | Kruthika Virupakshappa | Offline map of the HPWREN tower network; every detection becomes an incident with severity, county, camera bearing, tower wind and a downwind cone; frame-by-frame analysis panel; edge vs cloud cost per frame |
| `sentinel/geo.py`, `incidents.py` | Kruthika Virupakshappa | Bearings, least-squares triangulation across towers, consolidation of duplicate incidents, offline county lookup, incident store |
| `sentinel/watch.py`, `wind.py` | Kruthika Virupakshappa | Live watch (multi-tower FIgLib replay with growth tracking and escalation); tower weather-station emulation; downwind cone |
| `sentinel/assistant.py` | Kruthika Virupakshappa | "Ask Sentinel": the on-device 7B plans schema-constrained tool calls over the local incident store and answers from those facts only |
| Integration | Project | Joint detector at 960 px for tower frames (D-Fire model at 640 px for photos), `--state-dir` isolation, `start_demo.sh` step, demo runbook segment; review fixes (incident lock, per-step demo errors, assistant tool errors, input validation) |

## Models

Unchanged from v1.3.0-joint: `joint_yolo.pt` (`b02da05a3dad327946a0ab64bfe62752a17ea2242d878a469a83053ca5fedc44`) for tower frames; `smoke_yolo.pt` (`a80bfcc80e0ab1ef7709be4b22a8540b68c69c2e782763d659b7b11b8f36c7f5`) for photos; LoRA adapter `context` (`ae325957b4b29dc6fe99c248ec2a293227834764a3cfab425e946d67b7fd32fe`) on Qwen2.5-VL-7B revision `cc594898137f460bfe9f0759e9844b3ce807cfb5`.

## Verified on the Nano (integrated build, fresh state)

| Check | Result |
|---|---|
| Demo scenarios, 11 photos | **11/11 matched** the expected severity (4 ALERT, 2 MONITOR, 3 LOG, 2 IGNORE at the detector) |
| Junction Fire live watch | One incident, **ALERT**, triangulated from **2** towers (Big Black, Mesa Grande), 65 frames |
| Beaver Fire live watch | **ALERT**, 37 frames, 8 situation updates |
| Tests | 457 passed (laptop and Nano) |

With the older stage-2 tower detector the same Junction watch saw 4 of 6 towers; the joint detector trades a little distant-plume sensitivity (tower mAP50 0.718 vs 0.728) for not forgetting close-range scenes (D-Fire 0.748 vs 0.106).

## Run

```bash
./scripts/start_demo.sh          # also starts the map on 8100 (own state dir) unless one is already running
ssh -N -L 8095:localhost:8095 -L 8090:localhost:8090 -L 8100:localhost:8100 hp11@<nano-ip>
```
One-time assets (map tiles, FIgLib recordings): `scripts/setup_map_assets.sh`, `scripts/fetch_figlib.sh`, `python scripts/build_cameras.py`.

## Known issues

- Holding the incident lock across a watch step means a map action can wait up to one VLM call during a live watch.
- Restoring the link with several queued ALERTs and no internet route can pause watch steps ~3 s per alert (forecast timeout).
- Model caveats from v1.3.0-joint still apply.

## Restore

```bash
git checkout v1.4.0-incident-map
cd ~/sentinel/models/versions/v1.3.0-joint && sha256sum -c SHA256SUMS
```
